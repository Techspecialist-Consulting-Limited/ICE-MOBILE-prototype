# NSIA ICE 2.0 mobile app

This repository's `/` route hosts a mobile-first, interactive ICE 2.0 staff app. Start it with `npm run dev`; run `npm run build` to check a production build.

## Demonstration boundaries

- Report submissions, alert acknowledgements, contact edits, notification reads, and SOS flow state are held in local React state. They are not sent to NSIA systems and are not persisted across reloads.
- Quick Reports are separate local demonstration events. Selecting a category first asks whether to send now or continue with the complete incident form. Quick sends create a local reference only on simulated success and can be enriched in place with required incident details without creating a second record. Offline mode produces a retryable failure without a reference.
- The Quick Report flow does not connect to a responder queue or dispatch service. Production Quick Report routing, authorization, and dispatch capability must be confirmed and approved before any live integration.
- The full incident report wizard keeps category, summary, description, location, date/time, and optional attachments in one local draft through Category, Details, Location & Date, Evidence, and Review. Its simulated current-location action selects a labelled demo location; it does not request GPS or access device location. Evidence stays in local browser memory and is not uploaded.
- Submitted reports can be opened from My Reports to review details and the confirmed status timeline, then supplemented without replacing the original report. Supplementary text and selected attachment names are held in local session state; files are not uploaded, and each selected file is limited to 10 MB.
- The SOS journey is an interaction preview only. No emergency contact or emergency service is notified, no dispatch is claimed, and no hold duration or escalation timer is assumed.
- Current-location actions use a labelled demo location; they do not access GPS or track device location.
- Alert and system-notification content is illustrative and is not live. Admin-issued alerts and system/report notifications are separate destinations and have independent categories and read/acknowledgement state. External sharing is available only for items explicitly classified as Shareable.
- The sign-in screen uses the NSIA logo and building image in `public/images`. Selecting “Continue with Microsoft” advances through a clearly disclosed local sign-in simulation; it does not collect credentials, contact Microsoft, or authenticate an account. Production authentication must use the approved organizational identity provider.

## App journeys

The entry flow opens directly on the Microsoft sign-in screen. The background image is used there. After the local sign-in simulation, a first-login welcome screen introduces the ICE workspace; Continue opens Home. Refreshing or starting a fresh session returns to sign-in, so the welcome screen appears after the next simulated sign-in. The Home header says “Greetings, Mike.” New sessions start with no submitted reports; reports created during a session are held in local app state. Use Profile → “Start fresh session” to clear session changes and return to sign-in. Profile also links to editable personal contact details, emergency contacts, Settings, and notification preferences. Organization-managed profile fields are read-only; critical safety alerts cannot be disabled, while incident and general safety updates can be changed for the current session. The curved bottom navigation opens Home, Alerts, Reports, and Profile around the separate central SOS action. Alerts uses a warning-triangle icon distinct from the notification bell and is the destination for admin-issued safety messages, categorized by Safety, Access, and Security; it supports search, alert details, and session-only acknowledgement. The notification bell in the Home header opens the separate Notifications destination, which contains categorized System, Account, and report-status updates; opening an item marks it read in the current session, and report updates link to their matching report where available. Both destinations use illustrative local content and are not connected to a live alert publisher or notification service. Reports opens the My Reports list, where search and status filters work; sent quick reports appear alongside full reports and open tracking details with a timeline of recorded events, including submission, retry, and any added details. The Home “Report with details” action remains a separate shortcut to create a new incident report. Choosing a Home category opens a confirmation dialog with “Send now” or “Send with details”. Successful quick reports appear in Recent activity rather than a duplicate confirmation card; they can be tracked or enriched using the same reference. The full report wizard supports Category, Details, Location & Date, Evidence, and Review. A quick report's Add details action opens the same wizard and updates its existing local event/reference. SOS follows an overview → explicit confirmation → processing → outcome → contact-status flow. Confirmation uses an accessible button rather than a timed hold because no approved hold duration is configured. The request, reference, and processing transition are local to the current session; no real contact notification, emergency-service dispatch, GPS capture, or escalation occurs. A retry reuses the existing request reference to avoid duplicates. Alert details, notification details, and emergency-contact editing are connected using local screen state. Form entries remain available when moving backward in the reporting flow.

Edit profile follows the provided design with a profile-photo selector, read-only organization details, and editable phone, personal email, blood group, genotype, gender, date of birth, and optional emergency medical notes. Profile-photo and personal/emergency field changes are held in local app state for the current session only.
